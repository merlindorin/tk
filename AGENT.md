# Agent-Specific Instructions

This file contains essential information for AI agents working on the `tk` project.

## Project Overview

**tk** is a CLI tool that bootstraps Go projects with pre-configured [Taskfile](https://taskfile.dev) powerpacks. It eliminates the need to copy boilerplate configuration files between projects by providing curated, reusable task configurations.

### Key Technologies
- **Language**: Go 1.25.5
- **CLI Framework**: [Kong](https://github.com/alecthomas/kong) for command-line parsing
- **Task Runner**: [Task](https://taskfile.dev/) for workflow automation
- **Embed**: Go embed.FS for embedding powerpack files into the binary
- **Tools**: golangci-lint v2, goreleaser v2, trufflehog v3, license generator

### Core Concept
Powerpacks are bundles containing:
- `Taskfile.yaml`: Reusable task definitions for specific tools (linting, formatting, CI/CD, etc.)
- `README.md`: Documentation explaining the powerpack's purpose and usage

## Architecture

### Directory Structure
```
tk/
├── cmd/tk/                      # CLI entry point
│   ├── main.go                 # Main application with Kong CLI definition
│   ├── commands/               # Command implementations
│   │   ├── commands.go        # Shared flags (--target, --dry-run) and change reporting
│   │   ├── init.go            # Initialize tk in a project (first time)
│   │   ├── update.go          # Update existing tk installation
│   │   ├── status.go          # Report drift between the project and the binary
│   │   ├── list.go            # List powerpacks and their state
│   │   ├── add.go             # Install powerpacks in a project
│   │   └── remove.go          # Remove powerpacks from a project
│   └── global/                # Global CLI configuration
│       └── tk.go
├── pkg/powerpacks/             # Core powerpack management logic (the only library package)
│   ├── manager.go             # Plan/apply engine: what tk would write, and writing it
│   ├── powerpack.go           # Powerpack data structure, I/O and checksum
│   ├── config.go              # .tk.yaml (options + provenance)
│   ├── taskfile.go            # Marker-based merge of Taskfile.yaml, and .envrc cleanup
│   └── templates.go           # Static content of the generated files
├── powerpacks/                 # Powerpack definitions (embedded in binary)
│   ├── powerpacks.go          # Builds powerpack manager from embed.FS
│   ├── claude/                # Claude Code AI agent configuration
│   ├── default/               # Default task patterns
│   ├── dependabot/            # Dependabot configuration
│   ├── git/                   # Git pre-commit hooks
│   ├── go/                    # Go build, test and coverage tasks
│   ├── golangci/              # golangci-lint configuration
│   ├── goreleaser/            # GoReleaser configuration
│   ├── install/               # Install/uninstall orchestration
│   ├── license/               # License generation
│   ├── tk/                    # Pins tk in go.mod and keeps .tk/ in sync
│   └── trufflehog/            # Secret scanning

    └── <powerpack>/           # Copied from powerpacks/ at runtime
        ├── Taskfile.yaml
        └── README.md
```

### Commands

| COMMAND | PURPOSE |
|---------|---------|
| `tk init` | Install tk in a project, recording the options in `.tk.yaml` |
| `tk update` | Re-apply `.tk.yaml` with the powerpacks of the current binary |
| `tk status` | Report what `tk update` would change, and which tk wrote the project |
| `tk list` | List every embedded powerpack with its task prefix and state (`installed`/`new`/`outdated`/`available`); `--tasks` lists the tasks it provides |
| `tk add <name>` | Add a powerpack to the selection |
| `tk remove <name>` | Drop a powerpack from the selection |

Every command takes `--target` (defaults to the working directory); the writing ones take `--dry-run`.

### Selecting powerpacks

`.tk.yaml` holds an **allow list**: `includes:` empty (or absent) installs every powerpack, naming some installs
only those. `tk init --include a,b` writes it, `tk add`/`tk remove` edit it. `Manager.Disable` materialises the
implicit selection before dropping a name, and refuses to empty it. The older `excludes:` deny list is still read
and converted by `Manager.normalize` on the next write.

### How tk Works

1. **Embedding**: All files in `powerpacks/` are embedded into the Go binary using `//go:embed *`
2. **Initialization**: `tk init` copies embedded powerpacks to `.tk/<powerpack>/` directory
3. **Generation**: Merges the powerpack includes into the root `Taskfile.yaml`, marking each generated line with a trailing `#!tk` comment (see `pkg/powerpacks/taskfile.go`). Only marked lines are rewritten; the rest of the file is preserved. `.envrc` is cleaned of the lines tk used to write there and removed when nothing else is left
4. **Configuration**: Saves options to `.tk.yaml` for future updates
5. **Updates**: `tk update` reads `.tk.yaml` and regenerates files from embedded powerpacks

### Key Design Decisions

1. **Embed Over Remote**: Powerpacks are embedded in the binary rather than fetched remotely for reliability and offline support
2. **`.tk/` Directory**: Generated files live in `.tk/` to separate them from source control and user code. `.tk/` is fully owned by tk and wiped on each run, while shared files (`Taskfile.yaml`, `.envrc`) are only edited line by line
3. **Marker-based merge**: `Taskfile.yaml` and `.envrc` are shared with the user, so tk only owns the lines carrying the `#!tk` marker (plus the legacy lines it generated before the marker existed: `.tk/<pack>/Taskfile.yaml` includes and the `TASK_X_REMOTE_TASKFILES` export). tk writes nothing to `.envrc` anymore — Task released that experiment and warns about the variable — so an update removes the line and deletes the file when it held nothing else
4. **Immutable Powerpacks**: The `powerpacks/` directory is the source of truth; `.tk/` is regenerated on update
5. **Tool Management**: Powerpacks use Go's tool directive (`go get -tool`) for managing development tools as project dependencies

## Development Workflow

### Building the Project
```bash
task go:build           # Build every command into ./bin
task go:tidy            # Tidy the go module
```

### Running Tests
```bash
task go:test            # Run the test suite (go test -race ./...)
task go:cover           # Run the tests with coverage and print the report
task golangci:lint      # Run linters
```

### Local Development
To test changes to powerpacks:
1. Modify files in `powerpacks/<name>/`
2. Run `go run cmd/tk/main.go init` in a test directory
3. Verify generated `.tk/` and `Taskfile.yaml`
4. Run `task --list-all` to verify task definitions

### Adding a New Powerpack
1. Create `powerpacks/<name>/` directory
2. Add `Taskfile.yaml` with task definitions
3. Add `README.md` with documentation
4. The `BuildPowerpackManager()` function auto-discovers it via `embed.FS`
5. Test with `tk init` in a clean directory

### Modifying Existing Powerpacks

**CRITICAL**: Powerpacks are templates that get copied to user projects. Changes affect:
- **This repo's `.tk/`**: Run `tk update` to regenerate
- **User projects**: Users run `tk update` to get changes

When modifying powerpacks:
1. Read the existing `Taskfile.yaml` file first
2. Understand the task structure and dependencies
3. Maintain consistency with other powerpacks:
   - Use `cmds:` (not `cmd:`) for task command lists
   - Use `env:` section for multiline content (not template variables)
   - Use `go install` for pre-compiled binaries (not `go tool` for external tools)
   - Follow conventional commit format for git commits
4. Update corresponding `README.md` if behavior changes
5. Test by running `tk update` in this repo
6. Verify with `task --list-all` and `task <powerpack>:default`

## Code Standards

### Go Code
- **Linting**: golangci-lint v2 with strict configuration
- **Formatting**: goimports (configured in the `formatters` section of `.golangci.yaml`)
- **Conventions**:
  - Conventional commits (feat:, fix:, docs:, etc.)
  - No naked returns in functions > 5 lines
  - Explicit error handling (no ignored errors)

### Taskfile Standards
- Use `cmds:` for command lists (plural), even for single commands
- Use `cmd:` only for delegating to another task
- Use `env:` section for multiline environment variables
- Use `summary:` for detailed help text
- Use `desc:` for short descriptions
- Always provide variable documentation in `summary:`

### Testing Philosophy
- Unit tests for core logic in `pkg/`
- Integration tests create temp directories (`t.TempDir()`) and assert on the tree tk produces
- Command tests build the command struct directly and capture output through its `Out` writer
- Tests use `github.com/alecthomas/assert/v2`; there are no mocks and no mock generation

## Powerpack-Specific Knowledge

### Go Tool Management
Modern Go (1.23+) supports managing tools via `go.mod`:
- **`go get -tool <pkg>@<version>`**: Adds tool directive to go.mod
- **`go tool <name>`**: Runs a registered tool (ONLY works for tools that compile with current Go version)
- **`go install <pkg>@<version>`**: Installs binary to $GOPATH/bin
- **Direct execution**: Run installed binary directly by name

Powerpack `vars:` that shell out (`sh:`) are evaluated by Task on **every** invocation, including for included
Taskfiles the command does not touch. They must never fail: `goreleaser` and `license` fall back to `git config`
or the directory name when `gh` is missing, unauthenticated or the project is not on GitHub.

**IMPORTANT**: Use `go install` + direct binary execution for external tools (trufflehog, golangci-lint, etc.) because:
- `go tool` tries to compile from source each time
- Source may not be compatible with newer Go versions (int/int64 type changes, etc.)
- Pre-compiled binaries are more reliable

### Powerpack Categories

1. **Tool Wrappers** (golangci, goreleaser, license, trufflehog):
   - Provide install/uninstall tasks
   - Provide run task for executing the tool
   - Generate CI/CD configuration files
   - Use `go install` for installation

2. **Orchestrators** (install, default):
   - Run multiple tasks by pattern matching
   - Use `task -a --json | jq` to discover tasks
   - Provide install/uninstall variants

3. **Toolchain wrappers** (go):
   - Wrap commands the project already has (`go build`, `go test`)
   - Install nothing, standardise how the project is built and tested

4. **Configuration generators** (dependabot, tk):
   - Write a file a third party reads (`.github/dependabot.yml`, a workflow) and stop
   - `tk` is the self-update powerpack: `go get -tool` pins tk in go.mod so Dependabot bumps it, and the generated
     workflow runs `tk update` and opens a pull request. It is excluded from this repository: pinning tk as a tool
     of itself would be circular

5. **Generators** (claude, git):
   - Generate configuration files
   - Create boilerplate content
   - Set up project structure

### Common Patterns

**Task delegation**:
```yaml
pre-commit:
  cmds:
    - task: default
```

**Environment variable for multiline content**:
```yaml
cmds:
  - echo "${CONTENT}" > file.txt
env:
  CONTENT: |
    Line 1
    Line 2
```

**Conditional commands**:
```yaml
cmds:
  - |
    if [ "{{.SKIP}}" != "true" ]; then
      echo "Running"
    fi
```

## Common Issues and Solutions

### Issue: `go tool <binary>` fails with compilation errors
**Solution**: The tool's source code is incompatible with Go 1.25.5. Use `go install` + direct binary execution instead.

### Issue: Changes to powerpacks not reflected
**Solution**: Run `tk status` to see the drift, then `tk update` to regenerate `.tk/` from embedded powerpacks.

### Issue: tk did not remove a powerpack I excluded
**Solution**: Excluding is done through `tk remove <name>` (or `excludes:` in `.tk.yaml`); the next write deletes its
files and its `#!tk` include.

### Issue: Task not found after adding to powerpack
**Solution**:
1. Verify `Taskfile.yaml` syntax with `task --list-all`
2. Check that powerpack is included in root `Taskfile.yaml`
3. Run `tk update` to regenerate includes

### Issue: Pre-commit hook not working
**Solution**:
1. Verify `.git/hooks/pre-commit` exists and is executable
2. Run `task git:install` to regenerate the hook
3. Check that powerpack tasks have `pre-commit` task defined

## Important Files

- **`powerpacks/powerpacks.go`**: Powerpack discovery and loading
- **`pkg/powerpacks/manager.go`**: Core orchestration logic
- **`pkg/powerpacks/templates.go`**: Static content for generated files (`#!tk` marker, fresh Taskfile skeleton)
- **`pkg/powerpacks/taskfile.go`**: Marker-based merge of the root `Taskfile.yaml`, and removal of what tk used to write to `.envrc`
- **`.tk.yaml`**: Project configuration and provenance (options, excludes, tk version, powerpack checksums); it is committed
- **`Taskfile.yaml`**: Root taskfile (only the `#!tk` marked includes are generated; the rest is yours to edit)
- **`go.mod`**: Lists all tool dependencies in `tool (...)` block

## Performance Considerations

- Embedded powerpacks are in-memory (fast, no I/O)
- `.tk/` regeneration is quick (simple file copies)
- Task discovery uses `task -a --json` (can be slow with many tasks)
- Pattern matching uses regex (ensure patterns are efficient)

## Security

- **Secret scanning**: trufflehog powerpack scans for leaked credentials
- **No credentials in code**: Use environment variables
- **No force push to main**: Protected branch
- **Pre-commit hooks**: Automated checks before commits
